# Known failures

What fails on studio-canvas after the tidy-up of 2026-10-28, and why. Each line is an app bug a check
found, not a check that is out of date; the check is left failing (or works around it, where it says
so) until the bug is fixed. Remove a line when its fix lands.

Last full runs on this Mac (2026-10-28): with 2 workers, 973 assertions passed and 1 failed
(`media`, below); with the default 4 workers, 2 to 4 checks fail, a different few each run.

## App bugs

None known.

## Flaky under load

With 4 workers on this Mac (an M4 mini), 2 to 4 checks fail in a full run, and which ones changes
from run to run. Each of them passes when run alone (`node e2e/run.mjs <check>.mjs`). They fail
because the machine is busy: a press, a glide or a page load takes longer than the check allows.
They are not failing because of the app. Seen in the last runs: `stage-scroll`, `media` and `frames` find
no empty spot; `camera-roundtrip`, `board-links`, `stage-gestures`, `pen-stage`, `card-phone`,
`highlighting`, the WebKit half of `drop-lands`, and `context`'s finger drag of a board. `DECKS_E2E_JOBS=2` mostly avoids it (one
flake in 66 checks), at twice the time (12 minutes).

## Not app bugs, but worth knowing

- The Rust tests' font files (`packages/stage/fonts/*.ttf`) are not in git: `npm run fonts -w packages/stage`
  fetches them, checked to the byte (`stage-goldens` does it itself). Without them every test that sets
  words skips quietly, which is how a glyph texture bug went unseen.
- Playwright's `locator.click()` scrolls its target into view first, and the stage is a scroll
  container now, so it can pan the canvas under the press: press by coordinates instead.

## The canvas in its frame (2026-10-29, not yet a full run)

The checks were moved into the canvas frame group by group; the whole suite has not been run since. What the groups still saw failing, each an app bug or gap:

### Group A notes

- board-links (rewritten for a card's links): every link case fails, an app gap in the frame. `card-surface.tsx` `followLink` resolves a link against the frame page and recognises a deck board only by `/api/board/` on the page's own origin, but in the frame a card's files are read at `/api/t/<ticket>/board/…` (origin "null"), so a link to a board is never handed to `onOpenBoard`; and anything else goes to `window.open`, which the frame's sandbox (`allow-scripts allow-downloads`, no `allow-popups`) refuses, and there is no frame→page message to open a link in a tab (only `open-app`). Failing: "a link to a board puts that board on the canvas" (+ beside, in view), "a link to another site opens in a tab", "a file that is not a board opens in a tab too", "a board link the deck cannot open says so".
- focus: "the pill's Comment opens the box straight away, not the small button" fails. The page's own canvas opened the popover with `open: true` (App.tsx `onComment: setCommenting({ ...comment, open: true })`); the frame's chrome (`frame/frame.tsx` `onComment` → `setComment(target)`, `apps/web/src/frame/chrome.tsx`) passes the target without `open`, so the pill's Comment shows only the small Comment button and needs a second press. Also noted: the pill now offers Delete beside Hide (the frame passes `onDeleteBoard`, both call canvas.delete on a harness); the check expects that now.
- per-agent: "…the selection with it" fails (back on Ada, nothing is selected). Likely `frame/host.tsx`: `fromFrame` (what the frame last said: camera, selected, mode) is kept across frames, but the frame is made again for each canvas; coming back to Ada the page restores `selected` to the board her frame last reported, the effect sees `selected === fromFrame.selected` and never sends `select` to the new frame. Resetting `fromFrame` when a frame starts would fix it (app change). "…and the camera went with it" passed on the second run and failed once (68% → 68%): a race between the landing and the new frame's first camera, not reproduced.

### Group B notes (e2e failures that need an app change)

- canvas-frame.mjs, "switching to a canvas of drawing lands on its drawing": the camera stays at {0,0,1}. App bug in packages/canvas/src/frame/host.tsx: the effect that sends the page's camera to the frame tracks only `[camera, glide]` (`on(...)`), and reads `end()` untracked and returns before `localCamera = camera` while there is no frame yet. A switch of canvas makes a new frame; the landing's camera is set while it starts, so the frame never hears it and starts on the stale `localCamera`. Fit afterwards works.
- stages.mjs, "…at the arriving zoom, the same for every stage": reads 100%, not 30%. Same host.tsx bug as canvas-frame.mjs: the arrival camera is set while the new canvas's frame is starting and never reaches it (the switch, the pill and the server all agree; only the camera is lost).
- camera-roundtrip.mjs, "A comes back where it was left" / "…still there a few seconds later": passes on some runs, on others zoom comes back 4 → 1. The same host.tsx race: the view kept for A is set as A's frame is being made, and is lost when it lands before the frame's port is up. canvas-frame.mjs passes on some runs for the same reason. All three (canvas-frame, stages' arriving zoom, camera-roundtrip) should pass once host.tsx sends the camera the page holds when the frame says hello (or tracks `end()` in that effect and sets `localCamera` before returning).

- same-drawing: "…and is put down" — after a drag in the frame, the engine's lifted set (__decksRust.lifted) still holds the dragged box and its arrow 15 s after the drop, though the drop landed ("…where it was dropped" passes). In the frame a person's edit goes to the harness from the frame (document.send → canvas.batch); the lift seems never to be released when the drawing that has the edit comes back. App behaviour in the frame (drawing.ts / frame backend), not the check.
- edits-wait: "chromium: a board hidden from its pill: no frame shows it as it was, with the server's answer 400 ms away" — in the frame a card's/board's Hide is `backend.call("canvas.delete", [path])` (frame.tsx boards.onHide), not an edit shown ahead of the answer, so for the lag (~40 of 141 frames) the board is still drawn. The page's canvas showed it gone at once. App gap in the frame (onHide should take the item off the drawing as an edit, as takeOff does for Studio).
- pen-stage (observation, check adjusted): in the canvas frame `__decksEngine.stats()` reported tiles 0, drawn [0,0], pictures 0 while the canvas was drawn (`__decksSheet.shown` > 0); `__decksEngine` looks like an engine made before the one on screen (stale global). The check now also accepts the sheet's count.
- APP BUG (affects several checks): in the canvas frame the stage's render worker never starts, so drawn items (notes, shapes, arrows, ink tiles) are laid out but NOT PAINTED — a red rectangle inserted over the wire has a __decksPenBox but nothing shows in a screenshot; `__decksEngine.stats()` says workerBackend "" and tiles 0, on the dev server and on the built app (:4876) alike. Cause: `startWorker` (packages/canvas/src/stage/engine.ts) falls back, in the sandboxed "null"-origin frame, to a module worker from a `blob:` URL; Chrome fires `error` on a module worker made from a `blob:null/…` URL at once. Tried in the frame: a `blob:` CLASSIC worker and a `data:text/javascript,…` MODULE worker both start and can `import()` the http script cross-origin. So the fix is likely a `data:` URL for the shim (or a classic blob shim using `import()`).
- note-edges: "<engine>: the stage draws with webgpu/webgl2" (workerBackend "") and "the note's edge is between the paper and the note" (the note is not painted: paper on both sides of its edge), and "WebGL 2's edge is WebGPU's" — all the render-worker bug above. "the note is on the stage" and "no errors" pass.
- APP BUG (affects many checks): the page's landing camera does not reach the canvas frame when it is set before the frame has said hello — the frame opens at {x:0,y:0,zoom:1} instead of framed on the canvas's boards (old page: fitted, ~20%). In packages/canvas/src/frame/host.tsx `keepInStep`, the camera effect `on([state.camera, glide])` returns before `localCamera = camera` when `end()` is not there yet, and `end()` is read untracked inside `on`, so neither startFrame (which sends `localCamera`) nor the effect when the port opens carries the landing. Checks that assume the canvas opens on its boards now press Fit first (`fitCanvas` in harness.mjs).
- stage-gestures: "the composer says a dragged item would be mentioned here", "…and letting go puts it in as a pill, with an icon of its own", "…and leaves the item where it was, because that was never a move", "a board dropped on the composer is a pill, named by its title", "…and the board did not move: that was a mention, not a drag" — APP GAP: a drag from the canvas onto the composer to mention what is dragged finds its target with `elementFromPoint(...).closest(".composer-box")` (packages/canvas/src/editor/dom/effects.ts) in the frame's own document; the composer is in the page, so in the frame the item/board is simply moved under the composer and no pill is made. Needs the frame to know the dock's box (it has `look.dock`) and ask the page, or the page to hit-test. (The check puts the moved item back so the rest of it runs.)
- Also seen (not a check failure): Playwright's locator.click() on a frame element sometimes lands on the page's side panel (the stage scrolls the target into view first); shapes presses its pill buttons by coordinates instead.

- card-editor: "a file dropped on a card goes into it as a file's chip" (and the chip's double-click after it) — app gap: the page's drop handler (`apps/web/src/app/files.ts:187`) asks `globalThis.__decksCardAt` to find a card under the drop, but that global lives in the canvas frame now; the frame hands the drop to the page (`upload`), which no longer finds the card and places the file on the canvas instead. The frame needs to say which card (and where in it) the drop landed on, or put it in the card itself.
- card-phone: "a picture carried by a finger drops between two of the card's blocks", "…riding below and right of the finger", "a tap on the picture in the card shows its properties" — in the canvas frame a finger's drag of a selected picture is taken by the browser: the frame sees pointerdown, two pointermoves, then pointercancel on the first touchmove (CDP touches on an iPhone 14 Pro context), so the picture never moves. It passed with the canvas in the page; likely touch-action/scroll handling across the frame boundary (the frame is sandboxed, possibly out of process). Needs an app look; the check is unchanged in what it asks.
- backends, context-loss, one-picture (Chromium and WebKit iPhone): "no navigator.gpu, the page and the worker draw with WebGL 2", "board pictures are put and drawn as pictures", "the WebGL 2 canvas is not blank", "the stage draws with WebGL 2 before", "given back, the engine starts again", "and draws the boards again", "…about a byte a pixel on the GPU", "…and come compressed, every board", and a "no errors" from `__decksEngine` going away — app bug: the stage's render worker does not come up in the canvas frame (see the IMPORTANT note below). `new Worker(<http url>)` from the sandboxed frame throws a SecurityError, `startWorker` falls back to a `blob:null/…` shim that imports the worker module, and that worker then fails to load (an error event, no message), so `workerBackend` stays empty, nothing of the boards is drawn by it and nothing is compressed.
- tile-pixels: every assertion — it waits for `__decksEngine.stats().workerBackend`, which never comes in the canvas frame (the render worker cannot start from the sandboxed frame: see backends above). Converted to read the stage in the frame; fails on the same app gap.
- IMPORTANT, app bug behind several failures: the stage's render worker never comes up in the canvas frame, WebGPU or WebGL 2, in Vite dev and in the built app alike (checked on the frame test server :4876 too: a `blob:null/…` worker is made by `startWorker`'s shim, but `__decksEngine.stats().workerBackend` stays "" and `tiles` 0). The worker's module load fails (an `error` event with no message when the shim imports `render.worker.ts` from the sandboxed frame). So whatever the worker paints as tiles (shapes, text, ink: the drawing) is not drawn in the frame; board pictures, cards, documents and apps (DOM or the page engine's pictures) still are. Checks failing on this: stage-shot ("the canvas draws both items …", every "is in the picture — no ink where the canvas draws it"), placeholder (the dashed edge / writer tag are never painted), tile-pixels, and the WebGL 2 parts of backends/context-loss/one-picture (above).
- drop-lands: "dropped, it is put down once the saved drawing has come" — the lifted box is put down when the render worker answers the drop (`engine.ts` deletes from `lifted` on the worker's message); with no worker in the frame (see the render-worker note) it stays lifted. Rewritten otherwise: the live-board half is gone (a board is only its picture), and the 400 ms hold-back is on the frame's writes (`/api/v1/canvas.…`, page.route) instead of the page's socket, since the frame reads and writes the canvas on its own line.
