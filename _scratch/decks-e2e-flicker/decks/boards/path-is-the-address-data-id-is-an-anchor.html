Yes — and the rule is: a path from the nearest named ancestor, or from the body

The address is id + path, and id may be "" — which means the body. Nothing in the editor needs an element to be named: it needs an element to be reachable, and the body always is. A flow document with no ids at all is fully editable, block by block, by path.

Board What anchors the address What the path walks
A component board The card's own data-id — so the address is stable while anything around it moves. Inside the card: its heading, its paragraph, a table cell.
A flow document Nothing but the root — id: "". Its blocks are not named and do not need to be. From the body down: the fourth block's second child, and so on.
Slides The root again — a deck's <section>s are the file's own markup. From the body. And this is where “handle on the element” earns its place: the script may present the slides in another order, so DOM order and file order differ — but the handle travels with the element, so a press still lands on the right node, and the path is counted in the tree, which is the file's order. Counting DOM siblings would address the wrong slide.
Markdown — No tree at all: the whole file is one source edit, as it is today.

The one server change this needs is three lines, and they are already written on the branch we archived: if (id === "") return find(document, (element) => element.nodeName === "body"), plus its refusal wording (“this board has no <body> to edit”). On main today an address is data-id only, which is why the component ops have to find the body themselves. Port it with the tree editor, not after it.

Why keep data-id where it exists: a path is a position, an id is a name

Insert a paragraph above a block Every path below it shifts by one. The same edit leaves #goal — and every path walked from it — exactly where it was. That is the whole reason a named component is addressed by its name.
data-id is also how an agent refers to a thing “Edit #risk” survives a reflow; “edit the fifth child of the body” does not, and reads as a coordinate rather than as a thing. The ops' summaries speak in names for that reason, and a rename is an op of its own.
But the editor must not depend on one Its address is a path from the nearest named ancestor or from the body — the same rule in both cases. Which is why the tree editor needs nothing from data-id except the anchors that happen to be there, and why a flow document does not need to gain a single id to become editable.
Either way, before is the guard A name survives a move and not a rewrite; a path survives nothing but is checked. Both are only safe to send because the server compares the words at the address before it writes — and refuses, so the client re-reads, and the user retypes on what is actually there.
